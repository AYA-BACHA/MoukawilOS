# MoukawilOS — Product Requirements Document (PRD)

> **Status:** Sprint 0 Baseline — Formalized from Verified Algerian Legal Framework & Prototype Specifications  
> **Target Audience:** Algerian digital and creative freelancers operating under the Auto-Entrepreneur framework (*Loi n° 22-23 du 18 décembre 2022*).

---

## 1. Compliance & Turnover Dashboard

### User Goal
Monitor real-time annual turnover against the statutory ceiling of 5,000,000 DZD, track progress toward preventative thresholds, and maintain visibility over upcoming administrative deadlines.

### User Flow
1. User logs in and lands on the main Dashboard.
2. User views top-level metrics: Annual Turnover (Current Year), Unpaid Receivables, and Days Until Next Statutory Deadline.
3. User inspects the Annual Ceiling Gauge showing percentage of the 5,000,000 DZD limit reached.
4. If turnover reaches 80% (4,000,000 DZD), user sees a preventative warning banner.
5. If turnover exceeds 5,000,000 DZD, user sees a ceiling exceeded alert with the consecutive-year radiation counter.
6. User reviews the "Upcoming Obligations" widget showing prioritized tax and social security tasks.

### Inputs
- Fiscal year selection (default: current calendar year).
- Filter toggle for invoice aggregation (collected cash vs. total billed).

### System Behavior
- Aggregates turnover strictly from paid/collected invoices within the active calendar year (1 Jan – 31 Dec) per *CIDTA art. 282 sexies*.
- Computes percentage: `(Collected Revenue / 5,000,000) * 100`.
- Flags 80% threshold reached (4,000,000 DZD) with explicit label: `[Fonctionnalité MoukawilOS - Alerte Préventive]`.
- Evaluates consecutive years exceeding 5,000,000 DZD based on historical yearly totals (*Loi 22-23 art. 13-14*).
- Displays obligation cards generated by the calendar calculation engine.

### Outputs
- Annual turnover metric formatted in DZD (`### ###,## DA`).
- Visual progress bar / gauge for the 5M DZD ceiling.
- Status badge: `Sous le plafond`, `Alerte 80%`, or `Plafond dépassé`.
- Consecutive-year tracking indicator (Year 1, 2, or 3 with radiation notice).
- List of 3 nearest upcoming administrative obligations with status badges.

### Acceptance Criteria
- Dashboard turnover matches the exact sum of invoices marked `paid` for the selected year.
- At 4,000,000 DZD, an alert triggers clearly indicating preventative nature.
- At 5,000,001 DZD, status changes to exceeded; radiation notice triggers if exceeded for 3 consecutive years.
- Zero references to fictional quarterly CASNOS deadlines or monthly tax declarations.

### Dependencies
- Invoice Management (payment status updates).
- Deterministic Calculation Engine (`calc.ts`).

## 2. Invoice Creation & Mandatory Statutory Mentions

### User Goal
Issue commercial invoices that strictly comply with Algerian invoicing requirements (*Décret exécutif n° 05-468*) and auto-entrepreneur status rules (*Loi n° 22-23*).

### User Flow
1. User navigates to Invoices and clicks "New Invoice (Nouvelle facture)".
2. User selects an existing client or enters new client details (Name, Address, NIF if business).
3. System verifies user profile completeness (checks for 15-digit NIF and ANAE card number).
4. User enters invoice date, payment due date, and line items (Description, Quantity, Unit Price in DZD).
5. System computes subtotal and total in real time.
6. User views mandatory statutory notices previewed automatically.
7. User saves as `draft` or clicks "Finalize Invoice (Émettre la facture)".

### Inputs
- Client Information: Client name / company name, address, client NIF (optional for individuals, mandatory for corporate clients).
- Invoice Metadata: Issue date, due date.
- Line Items: Item description, quantity, unit price (DZD).
- Payment terms / notes (optional).

### System Behavior
- Auto-generates sequential, gapless chronological numbering in format `FA-YYYY-NNN` (e.g., `FA-2026-001`).
- Pulls seller profile data: Full name, business address, registered ANAE activity title, 15-digit NIF, RNAE card number.
- Injects mandatory VAT exemption text:  
  *« Franchise de TVA — Article 282 sexies du CIDTA — TVA non applicable »*.
- Injects commercial register exemption notice:  
  *« Dispensé d'immatriculation au Registre du Commerce (Loi n° 22-23 du 18 décembre 2022) »*.
- Computes `Total = Sum(quantity * unit_price)`. No VAT or tax line is calculated.
- If seller NIF or RNAE card number is missing, issuance is blocked with redirect to Settings.

### Outputs
- Created invoice record in database.
- Generated chronological reference number.
- Immutable state upon finalization.

### Acceptance Criteria
- Sequential numbering is strictly incremental per calendar year without duplicates or gaps.
- Missing seller NIF or ANAE number prevents invoice finalization.
- Mandatory VAT exemption notice is present verbatim on every invoice.
- No VAT amount or tax addition appears in invoice calculations.

### Dependencies
- User Settings (NIF, RNAE card number, approved activity).
- Database client and invoice tables.

## 3. Invoice Immutability & Credit Notes (Factures d'Avoir)

### User Goal
Correct billing mistakes, handle cancellations, or adjust invoiced amounts without violating the legal requirement of invoice immutability (*Décret exécutif n° 05-468, art. 11*).

### User Flow
1. User opens an already finalized invoice (`FA-YYYY-NNN`).
2. "Edit" and "Delete" actions are disabled/hidden.
3. User clicks "Issue Credit Note (Établir un avoir)".
4. User enters adjustment reason (e.g., partial refund, billing error, cancellation) and item adjustments.
5. User confirms creation.
6. System generates a linked Credit Note (`AV-YYYY-NNN`) and updates turnover metrics.

### Inputs
- Original invoice reference ID.
- Reason for credit note.
- Adjusted line items / amount to credit (in DZD).

### System Behavior
- Enforces database and API-level immutability on finalized invoices (no `UPDATE` or `DELETE` permitted).
- Generates linked credit note with sequence `AV-YYYY-NNN`.
- Injects mandatory reference: *« Avoir se rapportant à la facture FA-YYYY-NNN du DD/MM/YYYY »*.
- Automatically deducts the credit note amount from net annual collected turnover.

### Outputs
- Finalized Credit Note record (`AV-YYYY-NNN`).
- Audit link between original invoice and credit note.
- Updated net turnover on Dashboard.

### Acceptance Criteria
- Finalized invoices cannot be modified or deleted via UI or REST API.
- Credit notes strictly reference the parent invoice number and issue date.
- Turnover calculation correctly reflects `Total Paid Invoices - Total Credit Notes`.

### Dependencies
- Invoice Creation module.
- Calculation Engine.

## 4. Invoice Preview & Client-Side PDF Generation

### User Goal
Preview and export a clean, professional, print-ready PDF invoice to deliver to clients via email or messaging.

### User Flow
1. User clicks "Preview (Aperçu)" or "Download PDF (Télécharger PDF)" on any invoice.
2. A modal or dedicated screen displays the formatted invoice document.
3. User verifies all legal mentions and item breakdowns.
4. User clicks "Download PDF".
5. PDF is generated immediately in the browser and downloaded to local storage.

### Inputs
- Invoice ID.

### System Behavior
- Uses `@react-pdf/renderer` on the frontend for deterministic rendering.
- Applies standard Algerian invoice layout: seller details top-left, client details top-right, invoice metadata top-right, item table center, total in DZD bottom-right, statutory notices in footer.
- Includes 10-year archiving reminder: *« Document à conserver pendant dix (10) ans (Code de commerce art. 12) »*.

### Outputs
- Binary `.pdf` file downloaded locally with name format `Facture_FA-YYYY-NNN.pdf`.

### Acceptance Criteria
- Generated PDF contains every mandatory statutory field.
- Layout remains aligned and legible on standard A4 format.
- Generates client-side without relying on external network rendering services.

### Dependencies
- Invoice Creation module.
- `@react-pdf/renderer` in `frontend/`.

## 5. Income & Payment Tracking (Encaissements)

### User Goal
Track invoice settlement status to differentiate between billed receivables and collected cash revenue for accurate tax base reporting (*CIDTA art. 282 quater & sexies*).

### User Flow
1. User navigates to Invoices list.
2. Invoices display clear status badges: `Draft (Brouillon)`, `Pending (En attente)`, `Paid (Encaissée)`, `Overdue (En retard)`, `Credited (Avoir émis)`.
3. User clicks on a pending invoice and selects "Record Payment (Enregistrer le paiement)".
4. User inputs payment date and payment method (Virement bancaire, Chèque, Espèces, CCP).
5. System marks invoice as `Paid` and updates cash-basis turnover.

### Inputs
- Invoice ID.
- Payment date (default: today).
- Payment method (Virement, Chèque, Espèces, CCP).
- Transaction / payment reference note (optional).

### System Behavior
- Transitions invoice state from `pending` to `paid`.
- Records timestamp and payment method in database audit trail.
- Only invoices with status `paid` contribute to the annual IFU tax base and 5M DZD ceiling.

### Outputs
- Updated invoice status badge.
- Instant recalculation of Dashboard collected revenue.

### Acceptance Criteria
- Billed but unpaid invoices do not increase the IFU tax calculation or ceiling gauge.
- Marking an invoice as paid immediately updates the turnover total for the corresponding payment year.

### Dependencies
- Invoice Management.
- Supabase Database persistence.

## 6. Deterministic Compliance & Tax Calculation Engine

### User Goal
Calculate exact IFU tax and CASNOS social security liabilities with zero guesswork, and track all official filing and payment deadlines.

### User Flow
1. User navigates to the "Compliance (Conformité)" page.
2. User reviews verified statutory parameters: IFU rate (0.5%), minimum tax (10,000 DZD), CASNOS options.
3. User views their current calculated obligations based on year-to-date collected turnover.
4. User can use the "Statutory Simulator" to enter hypothetical revenues and see exact tax and CASNOS outcomes.
5. User consults the "Administrative Obligations Calendar" displaying upcoming filing dates.

### Inputs
- Current collected turnover (from system invoices).
- Simulator custom turnover amount (optional).
- CASNOS contribution option (Forfait auto-entrepreneur 24,000 DZD vs. Régime général 15%).

### System Behavior
- **IFU Calculation:**
  - Formula: `Max(10,000 DZD, Turnover * 0.005)`.
  - Stated statutory basis: *Loi de Finances 2024, CIDTA art. 282 sexies & 365 bis*.
  - Installment breakdown (if chosen): 50% by June 30, 25% Sept 1-15, 25% Dec 1-15 (*CIDTA art. 365*).
- **CASNOS Calculation:**
  - Option 1 (Forfait): Flat 24,000 DZD / year (*Décret exécutif 26-257*).
  - Option 2 (Régime général): 15% of declared income, bounded by floor of 43,200 DZD (1x SNMG 288,000 DZD) and ceiling of 864,000 DZD (20x SNMG 5,760,000 DZD).
- **Obligations Calendar:**
  - NIF Declaration (G n° 8): Within 30 days of ANAE card issuance.
  - IFU Provisional Declaration (G n° 12): By June 30.
  - CASNOS Annual Payment: By June 30 (annual unique payment).
  - IFU Installment 2: By September 15.
  - IFU Installment 3: By December 15.
  - IFU Definitive Regularization (G n° 12 bis): By January 20 of year N+1.
- Displays prominent disclaimer: Informational tool only; users are directed to DGI, ANAE, and CASNOS for official filings.

### Outputs
- Calculated IFU amount and installment breakdown.
- Calculated CASNOS amount.
- Timeline of chronological obligations with dynamic badges (`Accomplie`, `Dans X jours`, `En retard`, `À venir`).

### Acceptance Criteria
- 100% adherence to verified test cases:
  - Turnover 0 DZD → IFU = 10,000 DZD.
  - Turnover 1,850,000 DZD → IFU = 10,000 DZD (1,850,000 * 0.005 = 9,250 < 10,000).
  - Turnover 3,000,000 DZD → IFU = 15,000 DZD.
  - Turnover 5,000,000 DZD → IFU = 25,000 DZD.
  - CASNOS Flat = 24,000 DZD.
  - CASNOS General below floor (< 288,000 DZD) = 43,200 DZD.
  - CASNOS General above cap (> 5,760,000 DZD) = 864,000 DZD.
- No quarterly CASNOS deadlines exist.
- No monthly declaration deadlines exist.

### Dependencies
- Shared calculation library (`calc.ts`).

## 7. Regulatory RAG Assistant

### User Goal
Obtain accurate, verifiable answers to Algerian auto-entrepreneur administrative, fiscal, and regulatory questions, with explicit citations to official texts.

### User Flow
1. User navigates to the "Regulatory Assistant (Assistant Réglementaire)" page.
2. User sees an intellectual honesty notice stating answers are sourced strictly from verified Algerian statutes.
3. User types a question in natural language (French, Arabic, or English).
4. System retrieves context from the verified regulatory corpus and generates an answer.
5. User reads response accompanied by source badges (`verified-official`, `secondary-only`, `conflicting`, `unknown`), legal article citations, and official links.
6. If the question cannot be answered from verified sources, system returns an honest fallback directing user to DGI/ANAE/CASNOS contacts.

### Inputs
- User natural language question.
- User session / language preference.

### System Behavior
- Vector search retrieves relevant passages from indexed corpus (Loi 22-23, CIDTA articles, Décrets 23-196, 23-197, 15-289, 26-257, 05-468).
- LLM generates concise response constrained strictly to retrieved context.
- Formats response with explicit statutory citations and verification status badge.
- Strictly refuses to speculate on unindexed or unverified legal rules.

### Outputs
- Formatted answer with highlighted statutory references.
- Source attribution metadata: Article, law/decree number, official gazette reference.
- Confidence / status badge.

### Acceptance Criteria
- Every legal claim in the assistant output includes an identifiable legal citation.
- No fabrication of tax rates, decree numbers, or procedural deadlines.
- Unanswerable queries return the structured official fallback notice.

### Dependencies
- Backend REST API (`/api/assistant/query`).
- RAG Service (`rag/app/main.py` + `pgvector`).

## 8. Explicitly Excluded Features (Out of Scope for MVP)

To maintain focus and avoid scope creep, the following features are **explicitly excluded** from the MVP:
- ❌ **Payment Gateways & Processing:** No SATIM, CIB, or BaridiMob online payment processing.
- ❌ **Expense Tracking & Deductions:** Auto-entrepreneurs under IFU are taxed on gross turnover; expense deduction logic is inapplicable and excluded.
- ❌ **Multi-Currency Bookkeeping:** All invoices and calculations are strictly in Algerian Dinars (DZD).
- ❌ **Commercial Register (CNRC) Integration:** Auto-entrepreneurs are legally exempt from registration at the CNRC (*Loi 22-23 art. 2 & 11*).
- ❌ **Generic Social/Community Features:** No social feed, public forum, or freelancer marketplace.
- ❌ **Automated Tax Filing Submissions:** Platform does not file directly with the tax portal (Jibayatic); it generates figures for user manual declaration.
